# M3 执行中的决定

执行 `2026-10-28-m3-checkpoints-and-forks.md` 时，计划没写到、写错了或实测推翻了的地方，每完成一个任务追加。每条写：发现了什么、怎么定的、定错了的代价。M3 结束时并进 ADR-011 和 PR 描述。

## Task 1：引擎的分叉、提交条目和运行开始钩子

- **运行开始钩子的约定放在 core。** 第一版只是 `openPiEngine` 的一个选项，第二阶段自研引擎时看不到这条约定，testkit 也不检查（作者审阅时指出）。现在 `ports.ts` 定义 `RunStartListener` 并写明三条约定：每次请求模型之前都调用；参数是触发这一轮的提交，steer 进来的输入不改变它；回调抛错不打断这一轮。三条都在 AgentEngine 一致性测试里，pi 适配器不接钩子时有 2 个用例失败。代价：无。
- **core 的 FakeEngine 不跑一致性测试**（M1 以来如此），只按同样语义补上 `submissionEntry`（条目 ID 全局递增）和 `fork`。代价：替身与真实语义偏离时，core 的测试可能放过错误；Task 6 用到时再加强。
- **分叉查找存档的规则要改（Task 6 执行）。** 存档对齐的是这一轮的用户条目 U，内容是 U 之前的工作区。计划只取 `entryId ≤ E` 的最新一张，最常见的"在我这条消息之前分叉"（E 是 U 前一条助手回答）会退到上一张存档，并多列一轮"没有发生的操作"。改为：先取 `entryId ≤ E` 的最新一张 C；再看 `entryId > E` 的最早一张 C'，如果 E 和 C' 之间没有执行过 `write`、`edit`、`bash`，C' 与 E 时刻完全一致，优先用 C'。代价：多读一段记录；判断错会选到含有未来改动的存档，所以只在区间内没有这三种工具调用时才用。
- 测试确认了两个前提：分叉后新写的条目 ID 大于父会话的全部条目；steer 输入并进当前一轮，`run.inputs[0]` 不变（m0-findings §7 留下的缺口）。

## Task 3：工作区改为镜像文件

- **loop 设备一律用 `losetup --associated` 查找。** 第一版读 `/sys/block/loopN/loop/backing_file` 按路径比较。实测在容器里接上的设备，那里记的是相对于绑定挂载的路径（`/probe1/disk.img`），永远比不上，第一轮测试因此在测试机上泄漏了 20 个 loop 设备（已清理，只清测试镜像的设备）。`--associated` 按设备号和 inode 比较，在一次性特权容器里执行。代价：启动已停止的沙箱前多一次一次性容器，约 0.4 秒。
- **`diskMb` 最小 300。** xfsprogs 6.6 的 `mkfs.xfs` 拒绝小于 300 MB 的文件系统。`Unsupported` 增加 `minDiskMb`，组装层设 300，创建 agent 版本时就拒绝；provider 准备工作区时再挡一次，防止 `TETHER_DEFAULT_DISK_MB` 配得过小。512 MB 的镜像实际可用约 448 MB（XFS 日志和元数据）。代价：不能要比 300 MB 更小的工作区。
- **容器的 SandboxSpec 记在标签 `tether.spec` 里。** 启动前发现卷记着的 loop 设备不再接着本会话的镜像（宿主重启后编号变了或被别的镜像占用），就按标签删掉并重建容器；数据在镜像里，只丢容器层。计划只说"按原参数重建"，没说参数从哪来。代价：`docker inspect` 能看到 `setup` 命令（看不到会话变量的值）；M2 建的容器没有这个标签，镜像模式下无法这样重建（见 CHANGELOG 的升级注意）。
- **`perRun` 暂时仍然拒绝。** `UNSUPPORTED_IN_M3` 默认 `{ diskMb: true, approval: true, checkpoints: true }`，组装层按存储模式放开 `diskMb`；`checkpoints` 等 Task 5 接好钩子再放开，否则配置被接受却没有效果。代价：无。
- **大部分 Docker 测试仍走目录模式。** app、cli、sdk 和 fence、exec-pienv、sandboxes 的 Docker 测试数据目录在 `/tmp`（ext4），自动选目录模式，原样保留（它们直接读宿主上的工作区文件）。镜像模式由 sandbox-docker 的两套模式各跑一遍，加 app.docker 里一个 XFS 上的端到端用例覆盖。代价：镜像模式下的崩溃恢复、CLI、SDK 路径要到 Task 11 的端到端验收才覆盖。
- **provider 的 `checkpointRoot` 选项推到 Task 4。** Task 3 只在 Config 和启动探测里用它（与 `workspaceRoot` 同一个文件系统才选镜像模式）。代价：无。

## Task 4：后端的快照能力

- **快照文件的管理单独放进 `snapshots.ts`。** 计划把这些都写在 provider 里；provider 已经接近 300 行，快照 ID 的校验、路径、先写 `.tmp` 再改名、列出和磁盘空间拆出去，provider 只负责暂停、`sync`、恢复容器。代价：无。
- **`capabilities.fork` 仍为 false。** 这一项表示后端原生分叉（Cube）；Docker 的分叉由 core 用快照加 `create({ from })` 组合，能力表照 spec §4.2 写"用快照模拟"。代价：无。
- **从快照创建时大小跟着快照，`diskMb` 不起作用。** 镜像是整个克隆过来的，要改大小得另做扩容；恢复和分叉都应该和原来一样大。代价：同一个会话分叉前后改了 agent 版本的 `diskMb`，分叉出来的会话仍是旧大小。
- **暂停是必需的（实测）。** 把暂停去掉再跑"后台进程持续写入时存档"的用例，镜像模式立即失败；目录模式三次都碰巧通过（`rsync` 先后拷 `a`、`b` 只隔几微秒），所以这条用例对镜像模式是确定的检查，对目录模式是概率性的。
- 写满的工作区 `df` 按 MB 取整显示可用 0 或 1 MB，用例按"不超过 1 MB"判断。

## Task 5：每轮存档

- **没有沙箱时也记一条存档，快照为 null（模板）。** 计划写的是"没有沙箱就不存"。但钩子在一轮里每次请求模型前都会调用：第一轮开始时没有沙箱、跳过，这一轮的工具调用建出沙箱后，下一次请求前的钩子会发现"这个提交还没有存档、沙箱也在"，在半轮的状态上存一张，对齐到这一轮的用户条目，内容却已经含有这一轮的改动。改为记一条 `snapshotId: null` 的记录：它表示"这一轮开始时工作区就是模板"，同时按提交 ID 挡住同一轮后面的调用。`CheckpointRecord.snapshotId` 改为可空，第 2 版表结构的 `snapshot_id` 去掉 NOT NULL（第 2 版还没发布，直接改）。顺带的好处：在第一次工具调用之前分叉，可以精确地按模板新建，不必写"工作区已重置"。代价：每个 perRun 会话多一条不占磁盘的记录。
- **一轮开始时沙箱已丢失，这一轮指向最近一张存档的快照。** 丢失的沙箱在下一次工具调用时从最近的存档重建（Task 7），所以这一轮开始时的工作区就是那张；跳过不记又会碰上上一条的半轮问题。于是几条记录可以指向同一张快照。代价：Task 9 删快照前要确认没有别的记录还指向它；Task 7 重建时取存档的方式要和这里一致（目前这里只看本会话自己的存档，分叉出来、自己还没有存档的会话丢失时，这里记的是 null，Task 7 要么也按模板重建，要么把这里改成沿分叉链找）。
- **创建中、已销毁的沙箱不记。** 创建只发生在工具调用里、持有会话锁，钩子的存档拿同一把锁，等到创建结束；已销毁的会话已归档，不再有新的一轮。代价：无。
- **`UNSUPPORTED_IN_M3.checkpoints` 改为 false。** `AgentService` 的一个旧用例用默认值验证"不支持的字段被拒绝"，改用仍不支持的 `requireApproval`。

## Task 6：分叉

- **`findCheckpoint` 多一个参数 `read`，"下一张"规则在分叉链的每一级都用。** Task 1 定下的规则要看两条记录之间执行过什么，只靠 `AppStore` 做不到，于是加一个按会话读引擎记录的函数。每一级会话 L、上界 b：L 自己 b 之后的第一张存档，b 到它之间没有 `write`、`edit`、`bash` 就用它；否则 L 自己 b 之前最近的一张；都没有再往上一级，b 取 b 和分叉点中较小的。代价：每次分叉多读一段引擎记录（每页 100 条）。
- **一次工具调用按结果条目算发生时刻。** 调用条目和结果条目的 ID 不同；在调用之后、结果之前分叉，调用还没执行。按调用条目算，"下一张"规则会把这次调用漏掉，选到含有未来改动的存档。代价：没有结果的调用（崩溃中断的会被补上"已中断"的结果）不算发生。
- **说明从哪一刻开始列，由存储里的数据算出（`alignedEntry`）。** 存档在它那一级上界之前，从存档的条目往后列；在上界之后（"下一张"），从上界往后列。不能简单取 `min(存档条目, 分叉点)`：在上一级会话找到的"下一张"，条目 ID 可能落在本会话自己的条目中间，会漏列本会话自己的操作。只靠 `forkedFrom` 和存档记录就能算出来，所以分叉时和启动修复时用同一段代码写说明。代价：无。
- **启动修复补上引擎分叉后，说明交给组装层在 resume 之后写。** `recover()` 不写引擎（M2 的约定：resume 之前写会提前续跑），分叉说明和其他对账说明一起放进 `RecoverResult.notes`。代价：无。
- **分叉点先校验再写会话记录。** 条目 ID 不是正整数、或不在源会话的记录里，报 `invalid_request`，不留会话记录。计划的写法是"先写记录再分叉引擎"，条目不对时引擎分叉失败，留下一条启动修复永远补不上、只能标成 `failed` 的记录。代价：多读一次引擎记录（1 条）。
- **分叉会话的第一轮存档沿用分叉选中的存档（了结 Task 5 留下的问题）。** 分叉会话还没有沙箱时，第一次工具调用会从分叉选中的存档建沙箱，这一轮开始时的工作区就是那张；按 Task 5 的写法会记成模板，以后在这一轮分叉就错了。沙箱丢失、自己又没有存档时同样用分叉选中的那张。代价：Task 9 删快照前要确认没有别的存档记录还指向它（Task 5 已记下）。
- **选中的存档是模板（`snapshotId: null`）时按模板建沙箱、执行 setup，不另写说明。** 这一轮开始时还没有沙箱，模板加 setup 就是那一刻的状态。分叉时写的说明仍是固定的"已从存档还原"，文字不完全贴切，但对模型的含义（进程不在、工作区是那一刻的）一样。代价：无。
- **分叉之后、第一次工具调用之前，选中的存档被清理了：按模板建沙箱，执行 setup，写 `NOTES.forkFresh`。** 分叉时告诉模型的是"已还原"，这时要更正。存档记录还在而快照文件不在时，`provider.create` 报 `sandbox_failed`；Task 9 清理时记录和文件一起删，不会单独缺文件。代价：这次 setup 失败重试时会再写一次说明。
- **`tether.fork` 条目的 `data.missed` 是没有发生的操作的实际条数**，不是说明里列出的行数（超过 20 条时说明里多一行"and N more"）。
- **core 的 `FakeEngine` 补上真实语义（了结 Task 1 留下的问题）。** 按引擎会话保存记录，`transcript` 按 pi 适配器的方式分页，`fork` 复制分叉点之前的记录、条目不在时报 `invalid_request`，`appendEntry` 记下写入的说明。
- **CLI 测试用 HTTP 取条目 ID。** CLI 没有看会话记录的命令，用例直接请求 `/transcript` 拿第一条用户条目。这个 agent 的存档策略是 `none`，所以只覆盖"没有存档、按模板"的路径；从存档还原的路径由 app 的 Docker 端到端用例覆盖。

## Task 7：丢失后从存档恢复

- **重建用的存档改为 `restorePoint`：会话自己最新的一张，自己没有时用分叉选中的那张。** 计划写的是 `findCheckpoint(store, 会话, undefined)`，自己没有存档时会沿分叉链到上一级、以分叉点为上界重新挑一张。这和 Task 5 每轮存档在"这一轮开始时沙箱已丢失"时记下的那张、也和分叉会话第一次建沙箱用的那张可能不同，存档记录和实际恢复出来的工作区就对不上。两处现在都调用 `restorePoint`。代价：无。
- **最近的存档是模板（`snapshotId: null`）时按模板重建、执行 setup，说明用 `NOTES.reset`。** 那张存档就是模板，模板加 setup 和它一致；之后写的文件都没了，`reset` 的说法准确。代价：无。
- **说明里"之后执行过的操作"从存档对齐的那一刻列到会话最新的一条。** 存档属于本会话时从它的条目算；是分叉选中的那张时用 Task 6 的 `alignedEntry`。正在执行、触发重建的这次工具调用还没有结果，不在列表里。`SandboxService` 因此要读引擎记录，依赖从 `isRunning` 扩到 `isRunning | transcript`。代价：每次重建多读一段记录。
- **重建时 setup 失败，沿用原来的丢失原因。** M2 用内存里的表保留原因；原因进了绑定以后，新建的 creating 绑定没有原因，`abandon` 回 lost 时要把旧绑定的原因带过去，否则下次说明会变成 "missing"。代价：无。
- **从存档创建失败时绑定留在 lost，下次工具调用再试，不退回模板。** 照计划。存档记录在、快照文件不在时会一直失败；Task 9 清理时记录和文件一起删，启动对账也会处理没有记录的文件，不应出现只缺文件的情况。代价：真出现时这个会话的工具调用一直报 `sandbox_failed`，要手动删掉那条存档记录。

## Task 8：闲置删除档

- **`finalCheckpoint` 的签名改为 `(binding, take) => Promise<boolean>`。** 计划是 `(sessionId) => Promise<boolean>`，由 `CheckpointService.final` 自己经 `SandboxService.snapshot` 存快照。巡检处理一个会话时已经持有这个会话的锁，`snapshot` 又要拿同一把锁，会死锁。现在由巡检把"在锁里存快照"的函数 `take` 交给 `final`，`final` 只管判断要不要存、记存档。提交 ID 需要沙箱的创建时间，所以传整个绑定。代价：无。
- **最终存档对齐到会话最新的一条记录，含义是"这一条执行完之后的工作区"。** 和每轮存档"这一轮用户条目之前"的含义一致：用户条目本身不执行任何操作，两种说法指同一时刻；Task 6 判断"之间有没有改动"也是按结果条目算的。会话还没有任何记录、或没有引擎会话时不存。代价：无。
- **闲置时长按天写进原因，不足一天按分钟。** 原因会出现在给模型的说明里（`NOTES.restored`），测试机验收要把删除时间设成 120 秒，按天取整会写成 "0 days"。代价：无。
- **配置检查放在 `loadConfig`。** `TETHER_DESTROY_AFTER_SECONDS` 不大于 `TETHER_STOP_AFTER_SECONDS` 时报 `invalid_request`，和其他配置错误一样在启动时失败。`SandboxService` 本身不检查，core 的测试可以单独设两个值。代价：直接构造 `SandboxService` 的调用方要自己保证。
- **"会话不在运行才改 idle"放进 `#stoppedNote`。** 闲置停止的路径本来就先确认了不在运行；在 Tether 之外被停掉的路径没有确认，一轮正在跑时会话被改成 idle（M2 暂缓项）。代价：这条路径多一次 `isRunning`。

## Task 9：存档的清理与对账

- **快照文件按"还有没有记录用它"删。** Task 5 让沙箱丢失的那一轮沿用上一张快照，几条记录可以共用一张。删一条记录时先删记录，再看还有没有别的记录用同一张快照，没有才删文件。分叉引用按记录算就够了：被引用的记录不删，它用的快照文件也就一直有记录在用。先删记录、后删文件：两步之间崩溃，留下的是没有记录的文件，启动对账会删掉。代价：每删一张都要列一遍全部存档记录，稀疏化一次删很多张时是平方级，存档到上万张时要给 `AppStore` 加按快照查询。
- **稀疏化不删模板存档（`snapshotId: null`）。** 模板存档不占磁盘，删了省不出空间，反而丢掉"这一轮开始时是模板"的对齐信息。计划没提。代价：无。
- **残留的卷和 loop 设备按本实例 `workspaces/` 下的会话目录找，不按 loop 设备的 `backing_file` 找。** Task 3 实测过：在容器里接上的设备，`backing_file` 记的是相对于文件系统挂载点的路径，和宿主上的绝对路径比不上。现在列出 `workspaces/` 下有 `disk.img`、却没有容器的会话，删它的卷（`tether-<会话>`），用 `losetup --associated` 摘掉接着它的设备；镜像文件留着，丢失重建或归档时再删。这样不会碰到宿主上别的 loop 设备（测试机的 loop0），也不会碰别的 Tether 实例的卷。为此 `SandboxProvider` 加了 `releaseLeftovers()`，目录模式返回 0。代价：镜像文件已经被删掉、设备还接着的情况找不到（`remove` 先摘设备再删文件，正常流程不会出现）。
- **启动对账的顺序：修复会话 → 绑定对账、删孤儿容器 → 释放残留的卷和 loop 设备 → 快照对账 → resume。** 快照对账必须在 resume 之前：续跑的一轮会存新快照，那时它还没有记录，会被误删。代价：无。
- **`TETHER_CHECKPOINT_MIN_FREE_PERCENT` 接受 0 到 100（不含 100），0 表示不稀疏化。** 代价：无。
- **`SessionService` 的 `checkpoints` 依赖是可选的。** 只有组装层需要归档时清理存档，core 的其他测试不用给。代价：组装层忘了传就不清理；app 的接线由 Task 11 的端到端验收（"归档全部会话后 checkpoints 目录为空"）覆盖。
- **启动对账的 3 个用例没有看到"功能缺失"的失败。** 第一次运行时测试文件里一个字符串转义写错，整个文件没能加载。改为变异检查：在实现上把两步对账换成 0，3 个用例都失败，恢复后通过。

## Task 10：锁外拉镜像、docker 超时、准入计数

- **超时只杀 docker 命令行进程。** 用 `execFile` 的 `timeout` 和 `SIGKILL`，守护进程那边已经开始的操作（例如 `docker run` 正在建容器）可能继续完成。调用方按失败处理：`create` 失败时本来就会 `docker rm --force` 同名容器并删工作区；留下的其他残留由下次启动对账清掉。代价：极端情况下超时报错、容器却建好了，要等下次创建或启动对账才清。
- **超时的错误消息只写子命令名**（"docker run timed out after 120 s"）。`docker run` 的完整参数里有 `tether.spec` 标签，含 setup 命令，不该进错误消息和日志。代价：排查时看不到是哪个容器，要结合日志里的会话 ID。
- **`docker build` 不设上限**（`timeoutMs: 0`）。只在 `--build-sandbox` 这个一次性命令里用，可能要下载基础镜像。代价：无。
- **每次创建都先 `docker image inspect`。** 本地有镜像时多一次约 50 ms 的调用，换来拉取不占准入锁。重建、从存档创建也走这一步。代价：每次创建多一次 docker 调用。
- **"清理失败"的原因收成常量 `CLEANUP_FAILED`**，标记和准入计数用同一个值，避免两处字符串不一致。
- **Docker 测试不依赖外网。** 拉取失败用本机 1 号端口的"仓库"（连接立即被拒绝）；镜像已存在的情况用本地构建的默认镜像，它不在任何仓库里，真去拉就会失败。拉取成功的路径没有自动测试，留给 Task 11 的端到端验收。
- **改了旧用例的断言**：8 处写死了后端调用顺序的断言加上 `prepareImage`。

## Task 11：gVisor、端到端验收与文档

- **gVisor 下 1 个用例的断言改为按运行时区分。** 镜像模式的用例检查容器里 `/workspace` 的文件系统类型是 `xfs`；gVisor 里挂进来的目录都经它的文件代理，类型是 `v9fs`。这个断言要证明的是"挂的是镜像"，runsc 下改为只看容量（约 448 MB 可用、不超过 512）。写满报错、暂停一致性、loop 重新接等用例在 runsc 下原样通过，没有需要拒绝的组合。代价：runsc 下少一个"类型是 XFS"的直接证据。
- **验收发现的两个问题当场修复，没有留到最终审查。** 卷和容器同名导致容器被删后状态查询报错（`docker inspect --type container`），和删完快照留下空目录（`rmdir`）。都先补了失败的用例。`rmdir` 只在目录为空时成功；会话的最后一张快照只在归档清理时删除（稀疏化总留最新 5 张），这时不会再有新快照写进同一个目录，没有和存档并发的问题。代价：无。
- **验收脚本和记录进仓库**（`docs/acceptance/`）。计划只说"按 README 的 CLI 命令"；脚本可以在 M4 和以后的里程碑重跑。CLI 没有看会话记录的命令，脚本用 HTTP 取条目 ID，README 也照实写了。
- **README 示例换成验收的真实输出。** `tether checkpoints` 是 3 张，计划里写的"2 张"是 Task 5 加模板存档之前的说法。
- **gVisor 下发现目录模式快照的一致性问题，当场修复。** `rsync --link-dest` 默认按整秒比较修改时间，同一秒内改过、长度不变的文件会链接到上一张的旧内容。改为 `--modify-window=-1`（rsync ≥ 3.1.3）。剩下的风险是文件系统时间戳本身的粒度（内核按时钟节拍更新，约 1–4 ms）：在上一张快照之后几毫秒内改过、长度又不变的文件仍可能被当成没改。目录模式本来就是退路，README 推荐镜像模式。代价：rsync 低于 3.1.3 时负数会按 0 处理（只比整秒），README 写明需要 rsync ≥ 3.1.3。
