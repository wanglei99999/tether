# M3 执行中的决定

执行 `2026-10-28-m3-checkpoints-and-forks.md` 时，计划没写到、写错了或实测推翻了的地方，每完成一个任务追加。每条写：发现了什么、怎么定的、定错了的代价。M3 结束时并进 ADR-011 和 PR 描述。

## Task 1：引擎的分叉、提交条目和运行开始钩子

- **运行开始钩子的约定放在 core。** 第一版只是 `openPiEngine` 的一个选项，第二阶段自研引擎时看不到这条约定，testkit 也不检查（作者审阅时指出）。现在 `ports.ts` 定义 `RunStartListener` 并写明三条约定：每次请求模型之前都调用；参数是触发这一轮的提交，steer 进来的输入不改变它；回调抛错不打断这一轮。三条都在 AgentEngine 一致性测试里，pi 适配器不接钩子时有 2 个用例失败。代价：无。
- **core 的 FakeEngine 不跑一致性测试**（M1 以来如此），只按同样语义补上 `submissionEntry`（条目 ID 全局递增）和 `fork`。代价：替身与真实语义偏离时，core 的测试可能放过错误；Task 6 用到时再加强。
- **分叉查找存档的规则要改（Task 6 执行）。** 存档对齐的是这一轮的用户条目 U，内容是 U 之前的工作区。计划只取 `entryId ≤ E` 的最新一张，最常见的"在我这条消息之前分叉"（E 是 U 前一条助手回答）会退到上一张存档，并多列一轮"没有发生的操作"。改为：先取 `entryId ≤ E` 的最新一张 C；再看 `entryId > E` 的最早一张 C'，如果 E 和 C' 之间没有执行过 `write`、`edit`、`bash`，C' 与 E 时刻完全一致，优先用 C'。代价：多读一段记录；判断错会选到含有未来改动的存档，所以只在区间内没有这三种工具调用时才用。
- 测试确认了两个前提：分叉后新写的条目 ID 大于父会话的全部条目；steer 输入并进当前一轮，`run.inputs[0]` 不变（m0-findings §7 留下的缺口）。

## Task 3：工作区改为镜像文件

- **loop 设备一律用 `losetup --associated` 查找。** 第一版读 `/sys/block/loopN/loop/backing_file` 按路径比较。实测在容器里接上的设备，那里记的是相对于绑定挂载的路径（`/probe1/disk.img`），永远比不上，第一轮测试因此在测试机上泄漏了 20 个 loop 设备（已清理，只清测试镜像的设备）。`--associated` 按设备号和 inode 比较，在一次性特权容器里执行。代价：启动已停止的沙箱前多一次一次性容器，约 0.4 秒。
- **`diskMb` 最小 300。** xfsprogs 6.6 的 `mkfs.xfs` 拒绝小于 300 MB 的文件系统。`Unsupported` 增加 `minDiskMb`，组装层设 300，创建 agent 版本时就拒绝；provider 准备工作区时再挡一次，防止 `TETHER_DEFAULT_DISK_MB` 配得过小。512 MB 的镜像实际可用约 448 MB（XFS 日志和元数据）。代价：不能要比 300 MB 更小的工作区。
- **容器的 SandboxSpec 记在标签 `tether.spec` 里。** 启动前发现卷记着的 loop 设备不再接着本会话的镜像（宿主重启后编号变了或被别的镜像占用），就按标签删掉并重建容器；数据在镜像里，只丢容器层。计划只说"按原参数重建"，没说参数从哪来。代价：`docker inspect` 能看到 `setup` 命令（看不到会话变量的值）；M2 建的容器没有这个标签，镜像模式下无法这样重建（见 CHANGELOG 的升级注意）。
- **`perRun` 暂时仍然拒绝。** `UNSUPPORTED_IN_M3` 默认 `{ diskMb: true, approval: true, checkpoints: true }`，组装层按存储模式放开 `diskMb`；`checkpoints` 等 Task 5 接好钩子再放开，否则配置被接受却没有效果。代价：无。
- **大部分 Docker 测试仍走目录模式。** app、cli、sdk 和 fence、exec-pienv、sandboxes 的 Docker 测试数据目录在 `/tmp`（ext4），自动选目录模式，原样保留（它们直接读宿主上的工作区文件）。镜像模式由 sandbox-docker 的两套模式各跑一遍，加 app.docker 里一个 XFS 上的端到端用例覆盖。代价：镜像模式下的崩溃恢复、CLI、SDK 路径要到 Task 11 的端到端验收才覆盖。
- **provider 的 `checkpointRoot` 选项推到 Task 4。** Task 3 只在 Config 和启动探测里用它（与 `workspaceRoot` 同一个文件系统才选镜像模式）。代价：无。

## Task 4：后端的快照能力

- **快照文件的管理单独放进 `snapshots.ts`。** 计划把这些都写在 provider 里；provider 已经接近 300 行，快照 ID 的校验、路径、先写 `.tmp` 再改名、列出和磁盘空间拆出去，provider 只负责暂停、`sync`、恢复容器。代价：无。
- **`capabilities.fork` 仍为 false。** 这一项表示后端原生分叉（Cube）；Docker 的分叉由 core 用快照加 `create({ from })` 组合，能力表照 spec §4.2 写"用快照模拟"。代价：无。
- **从快照创建时大小跟着快照，`diskMb` 不起作用。** 镜像是整个克隆过来的，要改大小得另做扩容；恢复和分叉都应该和原来一样大。代价：同一个会话分叉前后改了 agent 版本的 `diskMb`，分叉出来的会话仍是旧大小。
- **暂停是必需的（实测）。** 把暂停去掉再跑"后台进程持续写入时存档"的用例，镜像模式立即失败；目录模式三次都碰巧通过（`rsync` 先后拷 `a`、`b` 只隔几微秒），所以这条用例对镜像模式是确定的检查，对目录模式是概率性的。
- 写满的工作区 `df` 按 MB 取整显示可用 0 或 1 MB，用例按"不超过 1 MB"判断。
