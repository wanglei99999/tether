# M4 混沌测试报告

2026-11-05 至 06 在测试机上运行（阿里云 2 vCPU、1.6 GiB 内存，Ubuntu 24.04，Docker 29，Node 22.23.4，gVisor release-20261019.0）。代码是 `m4-chaos` 分支 `d9fa6bb`，pi 1.4.0。计划：`docs/superpowers/plans/2026-11-05-m4-chaos-testing.md`，执行中的决定：`docs/superpowers/plans/2026-11-05-m4-rulings.md`。

```bash
npm run chaos -- --seed 20261105 --rounds 50 --keep-failed                    # runc，镜像模式
npm run chaos -- --seed 20261105 --rounds 50 --runtime runsc --keep-failed    # gVisor，镜像模式
npm run chaos -- --seed 20261105 --rounds 20 --storage directory --keep-failed # runc，目录模式
npm run chaos -- --scenario crash-loop                                         # 连续崩溃
```

## 做法

每轮启动一个 Tether 服务端（子进程）和 2 个会话，每个会话发 3 条消息，间隔 15 秒。假模型只看这次请求的对话内容决定下一步，所以服务重启后能接着走。每条消息让模型执行 3 条 `bash`：写文件、一条 3–8 秒的长命令、再写文件。每条命令往工作区的 `.chaos/exec.log` 记 `start`、`tick`、`end`。

每轮按种子生成 3 个故障，四种：

- `kill9`：`kill -9` 服务端，0–5 秒后重启。
- `stall`：对服务端持有的 `docker exec` 客户端发 `SIGSTOP`，2–40 秒后 `SIGCONT`。Docker 后端走本机 `docker exec`，没有网络可切，挂起它就是"连接卡住不断开"。
- `stallThenKill`：挂起后 1 秒再 `kill -9` 服务端，留下一个挂着的旧 daemon。
- `removeContainer`：`docker rm -f` 会话的容器。

40% 的故障落在某条消息发出后的 500 ms 内，为了碰到存档那约 0.3 秒的窗口。故障结束后每个会话再发两条消息，然后在随机一条用户消息处分叉，查分叉的工作区，最后归档全部会话。

## 检查的承诺

| 编号 | 承诺 | 怎么查 |
|---|---|---|
| I0 | 会话不卡死 | 故障结束后 180 秒内，每条消息都以 `done` 结束 |
| I1 | 同一个 `requestId` 最多一次运行 | 崩溃后用同一个 `requestId` 重发，记录里这条消息只有一条 |
| I2 | 不能重放的工具不执行两次 | `exec.log` 里同一个令牌至多一条 `start` |
| I3 | 重连后没有旧进程 | 新令牌 `start` 之后不再有旧令牌的 `tick` |
| I4 | 容器被删一定有说明 | 记录里有 `recovered`，模型收到了说明 |
| I5 | 已提交的条目客户端最终能看到 | 全程订阅的 SDK 事件流和记录接口的条目一致 |
| I6 | 分叉的工作区和说明一致 | 没有分叉点之后才写的文件；缺的文件出现在说明里 |
| I7 | 归档后没有残留 | 容器、卷、loop 设备、`workspaces/`、`checkpoints/` 都清空 |

检查函数本身的可靠性：每条承诺都有构造的违反样例（`chaos-invariants.test.ts`）；破坏性对照往容器的 `exec.log` 里再写一条已有的 `start`，驱动程序必须报 I2（`chaos.docker.test.ts`）。

## 结果

两次全量，同一个种子。第一次跑完后发现检查函数对 I6 误报，修好后跑了第二次。

| 组 | 轮数 | 用时 | 故障碰到 | 被打断的工具调用 | 第一次干净 | 第二次干净 |
|---|---|---|---|---|---|---|
| runc，镜像模式 | 50 | 0.91 h | 104/150 | 83 | 42 | 49 |
| gVisor，镜像模式 | 50 | 0.94 h | 105/150 | 90 | 46 | 50 |
| runc，目录模式 | 20 | 0.37 h | 44/60 | 37 | 17 | 17 |

第二次全量共 120 轮、2.22 小时，平均每轮 67 秒。

- "故障碰到"指故障发生时确实有东西可打：`kill9` 时会话在运行，`stall` 时找到了连接，`removeContainer` 时容器还在。没碰到的（约三成）多是落在两条消息之间。
- 两次全量里 I0 到 I5 一次都没有违反：没有卡住的消息，没有重复的请求，没有工具执行两次，没有旧进程活过重连，容器被删都有说明，事件流没有漏条目。
- 第二次的 4 轮违反都是 I7，是下面的 F2。

另外，`removeContainer` 之后、巡检发现之前的工具调用失败（"工具错误"约每轮 1.3 次），这是 README 当前限制里写明的行为，模型拿到错误后继续往下做。

## 发现的问题

### F1：模型请求期间连续崩溃 5 次，消息永远不结束

连续崩溃场景复现（`--scenario crash-loop --position model`）：模型 10 秒才回答，服务端每 3 秒 `kill -9` 一次，共 8 次，然后放它跑。

- pi 1.4.0 把这一轮的任务停下（`task_parked`，日志里一次），不再重跑。Tether 只把它记进日志。
- 放开后 180 秒，消息仍是运行中，客户端和模型都没有收到说明。
- 发一次中止，之后的新消息正常回答。

原因：pi 把"进程死时处于 running 的任务"各计一次，任务提交新状态后清零，到 `restartLimit`（默认 5）就停。工具调用和慢 `setup` 不触发：工具执行前先写执行意图，崩溃后得到"已中断"，算有进展（`early`、`spaced`、`tool`、`setup` 四个位置都是 `done`）。只有一直等模型回答、什么都没提交的任务会累积。

触发条件：服务端在同一次模型请求里连续崩溃 5 次，例如进程启动后很快 OOM、模型又慢。少见，但发生时静默卡住。

### F2：存档复制完后容器被删，快照文件留到下次启动

两次全量各 4 轮（runc 镜像模式 1 轮，目录模式 3 轮；第一次还有 runc 镜像模式 1 轮）。顺序是：

1. 存档 `docker pause` 后复制工作区；
2. 这时容器被删（`removeContainer`）；
3. `docker unpause` 失败（"is not paused"），存档记成失败；
4. 复制好的快照文件没有记录指向它，归档时删不掉。

下次服务启动时对账会删掉它（M3 的启动对账），所以是磁盘泄漏，不影响正确性。

## 没有覆盖的部分

- 宿主机重启、磁盘写满、OOM：测试机上不好安全地自动注入。宿主重启后重建失败会误删工作区（README 当前限制）仍未验证。
- 从存档恢复后，`exec.log` 也回到了存档时的内容，恢复前的执行记录查不到，所以 I2、I3 在恢复过的会话上只查了恢复之后的部分。
- 同一个种子产生同一份故障时间表，但进程调度不受控制，同一个种子不保证复现同一个交错。两次全量的失败轮次大多相同（runc 镜像模式第 5 轮、目录模式第 5、10 轮两次都失败），可以作为复现的起点。
- 只用了假模型。
