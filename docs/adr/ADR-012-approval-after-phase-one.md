# ADR-012：工具审批移到第一阶段之后

**状态**：已采纳
**日期**：2026-11-05
**决策人**：wangl

---

## 背景

设计文档 §3 把审批列为第一阶段目标：`permissions.requireApproval` 里的工具执行前要由用户批准，服务端在等待期间崩溃重启，审批请求仍在，批准后只执行一次。M3 时审批拆成单独一份计划，排在 M3 之后、M4 之前。

M3 合并后，审批要防的风险比立项时窄了。工作区里的破坏（例如 `rm -rf`）可以从每轮的存档恢复，分叉也能回到任意一轮之前。沙箱和存档都管不到的，是后果落在容器外面的操作：`network: "egress"` 的会话用传入的令牌执行 `git push --force`、调用外部 API、部署。`network: "none"` 且不传凭据的 agent，后果全部留在工作区里，审批几乎没有作用。

第一阶段还有一项重要的未验证内容：混沌测试（§11.3）。持久化和隔离的可靠性声明要靠它支撑，它也可能逼出代码改动。

---

## 备选方案

| 维度 | A：先做审批，再做 M4 | B：审批移到第一阶段之后，直接做 M4 |
|---|---|---|
| 第一阶段范围 | 做齐 §3 的全部目标 | 少一项目标，围绕持久化、隔离、存档收尾 |
| 发布时间 | 晚一份计划 | 早一份计划 |
| 需要出网和凭据的 agent | 执行前能拦 | 没有拦截手段，只能不给 `bash`（从 `tools` 去掉）或不开 `network: "egress"` |
| 返工风险 | 无 | 无：审批不碰沙箱，现有功能不依赖它 |
| 学习价值 | 补上持久化执行里"等人批准"这一块 | 推迟 |

---

## 决策

选 B。

1. 审批移到第一阶段之后，什么时候做由有没有真实需求决定，例如出现需要出网的 agent。§6.4 的设计和两条硬要求保留，不降级。
2. `permissions.requireApproval` 非空时继续报 `invalid_request`，不悄悄忽略，避免使用者以为有这层保护。
3. `POST /v1/sessions/:id/approvals/:callId` 不注册。
4. 下一步是 M4。

---

## 后果

- README 不能声称 Tether 能拦截危险操作。隔离和存档保护的是宿主和工作区，容器外的副作用由部署者通过 `tools` 和 `network` 控制。
- `permissions.denyTools` 现在只做校验（同时出现在 `tools` 里时报错），不是运行时拦截。
- 以后做审批时的已知线索：pi-durable 1.4.0 的工具任务先运行 `beforeTool`，再写执行意图（`src/harness/tool.ts`）。所以在钩子里等待时崩溃，重启后钩子会重新运行，工具不会执行两次，Tether 只需存待审批记录。这是读源码得出的，长时间等待会不会撞上 pi 的崩溃保护（`settings.restartLimit`）还没有实测。
