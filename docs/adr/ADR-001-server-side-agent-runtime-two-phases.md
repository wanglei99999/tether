# ADR-001：定位为服务端 agent 运行时，分两阶段实现

**状态**：已采纳
**日期**：2026-10-20
**决策人**：wangl

---

## 背景

项目最初的设想是"开源版的后台编码 agent"，类似 Codex Cloud：提交任务，agent 在远程环境里干活，完成后开 PR。讨论中发现，这类产品依赖的那一层机制（会话持久化与崩溃续跑、执行沙箱、实时事件流、agent 定义与版本）并不只服务编码 agent：豆包、ChatGPT 网页版、企业内部 agent，只要部署在服务端，都需要它。

项目还有两个目标：作者要借此掌握 harness 的底层知识（沙箱、持久化执行、远程执行协议、状态同步）；仓库是作者 GitHub 上的重点作品，设计的可讲述性和能跑同样重要。

pi 1.3.0 已经提供了这一层的大部分零件：`pi-durable`（持久化 agent 执行）、`pi-env`（远程执行 daemon 与客户端）、`chord`（状态同步），都标着 experimental。

---

## 备选方案

| 维度 | A：后台编码 agent 产品 | B：服务端运行时，全部用 pi | C：服务端运行时，先用 pi 再逐层自研 |
|---|---|---|---|
| 适用范围 | 只有编码场景 | 任何服务端 agent | 任何服务端 agent |
| 学到的东西 | 产品集成为主 | 组装 pi 的包 | 第一阶段组装，第二阶段每层亲手实现 |
| 跑通的速度 | 快 | 快 | 第一阶段快，第二阶段慢 |
| 对上游 API 变动的暴露 | 高 | 高 | 低：pi 只出现在适配层 |
| 作品的可讲述性 | 中 | 低：主要是胶水 | 高：每层都能讲"pi 怎么做、我怎么做、为什么不同" |

---

## 决策

选择 **方案 C**。

第一阶段用 pi 的现成包拼出完整系统，端到端跑通，所有行为测试通过。第二阶段保留 `pi-ai`（模型接入）和 agent 循环，把执行 daemon、沙箱后端、持久化引擎、事件同步逐个换成自己写的实现，上游代码只作参考。

两阶段能成立，靠两条硬约束：

1. 每一层前面都有 Tether 自己定义的接口，pi 的类型只出现在适配层。
2. 每一层都有一套与实现无关的一致性测试。第一阶段 pi 的实现是参照答案，第二阶段自己的实现必须通过同一套测试。

多 agent 管理 App 是第一个正式客户端，另外立项，只通过公开 API 使用运行时。

---

## 后果

**正面**：
- 运行时不绑定某一种 agent 或前端，可以复用到别的服务端场景。
- 第一阶段很快能有一个可用的系统；第二阶段每替换一层，都有现成的测试判断替换是否成功。
- 上游 experimental API 的变动只影响适配层。

**负面**：
- 接口和一致性测试是额外的工作量，第一阶段比直接调用 pi 慢。
- 接口要同时容纳 pi 的实现和以后自研的实现，设计时容易被 pi 的形状带偏，需要在评审时留意。
- 第二阶段的工作量大，尤其是持久化引擎，完成时间难以估计。
