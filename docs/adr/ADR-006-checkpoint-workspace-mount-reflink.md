# ADR-006：检查点用工作区挂载加 reflink，不用 docker commit

**状态**：部分被 ADR-011 取代（2026-10-28）：目录级 `cp --reflink` 改为每会话一个 XFS 镜像文件，"保留最近 5 个"改为每轮都留、按空间稀疏化；工作区挂载、只快照 `/workspace`、ext4 退回 rsync 仍然有效。M0 已验证（2026-10-24）。
**日期**：2026-10-21
**决策人**：wangl

---

## 背景

会话可以分叉到任意历史条目，沙箱的文件系统只有当前一份。检查点在对话的某个位置留一张文件系统快照，用于分叉、沙箱丢失后重建、以后的撤销。默认策略 `perRun` 在每轮运行开始前打一次快照，每个会话保留最近 5 个。

最初的方案是 `docker commit`。分析 overlay2 的机制后发现：容器的可写层记录的是创建以来的全部改动，对同一个容器反复提交，每一层都包含此前所有轮次的改动。示意估算：工作区 520 MB、每轮改 2 MB，5 个快照约 2.6 GB，其中约 2 GB 是重复存储。

调研了业界的做法：Replit 和 Fly.io Sprites 在块设备层做写时复制；CubeSandbox 用 XFS reflink（一次 `FICLONE` 只复制元数据）；Modal 的文件系统快照和 docker commit 同属镜像层；Replit 另外在每个检查点做一次 git 提交。

---

## 备选方案

| 维度 | A：docker commit | B：rsync --link-dest | C：reflink | D：块设备快照 | E：overlay 分层 |
|---|---|---|---|---|---|
| 5 轮额外空间（示意） | 约 2.6 GB | 约 528 MB | 约 10 MB | 只算变化的块 | 约 10 MB（只改小文件时） |
| 打快照 | 打包整个可写层 | 比较 + 复制改过的文件 | 元数据操作 | 元数据操作 | 冻结可写层、重新挂载 |
| 恢复 / 分叉 | 从镜像建容器 | 完整复制工作区 | 元数据操作 | 元数据操作 | 用已有的层重新挂载 |
| 粒度 | 文件 | 文件 | 块 | 块 | 文件（改大文件一个字节也复制整个文件） |
| 覆盖范围 | 容器内全部文件 | 挂载的工作区 | 挂载的工作区 | 整块磁盘 | 挂载的工作区 |
| 前置条件 | 无 | 无 | XFS（reflink=1）或 btrfs | 虚拟块设备与对象存储 | root 执行 mount；挂载传播；层数多了要合并 |

E 是 2026-10-24 补充的：测试机的系统盘是 ext4，B 的恢复要完整复制，于是考虑在 ext4 上自己管理 overlay 分层。docker commit 浪费空间是因为容器只有一个不断累积的可写层；每轮换一个新的可写层就不会重复存储。它的风险是打快照时容器里仍在运行的进程持有旧挂载，可能写进已经冻结的层。

---

## 决策

**工作区挂载 + reflink，不支持时退回 rsync 硬链接，不用 docker commit**：

- 工作区放在宿主机目录里，挂载进容器作为 `/workspace`，不写进容器的可写层。
- 宿主目录所在的文件系统支持 reflink 时，快照、恢复、分叉都用 `cp -a --reflink=always`。
- 不支持时（例如 ext4）用 `rsync -a --link-dest`，接受恢复时完整复制的代价。
- 快照只覆盖 `/workspace`，`kind` 恒为 `filesystem`。
- 快照打到一半崩溃留下的半成品，由启动对账清理：没有对应 `checkpoints` 记录的快照目录直接删除。

块设备层需要的基础设施单机 Docker 没有，不考虑。git 提交可以作为以后给用户看改动的补充，不作为检查点本身。

M0 的 Task 6 要实测四种做法（docker commit 反复提交、reflink、rsync 硬链接、overlay 分层）的耗时和空间占用，确认这个选择和"保留 5 个"的默认值。如果 overlay 分层的冻结层不会被运行中的进程写入、实测数据也明显优于 rsync，ext4 上的退路改为 overlay 分层。

部署建议：系统盘通常是 ext4，需要高效检查点的部署另挂一块数据盘格式化为 XFS 存放工作区（CubeSandbox 也要求 `/data/cubelet` 是 XFS）。

**M0 验证结果**（`spikes/m0/checkpoint.test.ts`，`docs/m0-findings.md` 第 6 节）。500 MiB 工作区连续打 3 次快照，两次快照之间各改动 2 MiB：

| 做法 | 每次快照 | 恢复 | 新增空间（新文件改动 / 大文件原地改动） |
|---|---|---|---|
| C：reflink（XFS） | 7–9 ms | 5 ms | 4.0 MiB / 4.1 MiB |
| B：rsync（ext4） | 新写文件：第一次 2468 ms，之后 63–238 ms；原地改动：每次 5.7–7.0 s | 2.2–5.4 s | 508 MiB / 1500 MiB |
| E：overlay 分层（ext4） | 43–56 ms | 57–67 ms | 4.0 MiB / 1000 MiB |
| A：docker commit | 13–16 s | 337–357 ms | 3016 MiB / 3000 MiB |

- A：同一容器连续提交三次，每层都是 53.5 MB，确认了重复存储；Docker 29 的 containerd 镜像存储下每次提交约占两倍层大小，比示意估算更贵。
- C 的耗时与工作区大小无关（0、50、500 MiB 三档都在 5–9 ms），首选成立。
- E 被否决：容器里有进程开着工作区文件时，普通卸载报 busy；延迟卸载后该进程继续写进已冻结的层（2 秒内 12 字节涨到 32 字节），内核报 `undefined behavior`。要得到可靠快照必须先结束这些进程，与 `perRun` 不打断后台服务的要求冲突。它也和 B 一样按文件复制，大文件原地修改时并不省空间。ext4 上的退路维持 B。
- 三种工作区做法都满足：文件恢复到快照时的版本、进程不恢复、恢复出的工作区与快照互不影响。

---

## 后果

**正面**：
- 支持 reflink 时，打快照和恢复都接近零成本，空间只随实际改动增长。
- 快照和容器解耦：容器删除后快照仍在，从快照重建只需挂载一个新目录。
- 与 CubeSandbox 的磁盘快照原理一致，第二阶段做对比时有共同的基础。

**负面**：
- `/workspace` 之外的改动（例如 `apt install` 装的包）不在快照里，恢复后会丢失，必须写说明。
- 服务器文件系统不支持 reflink 时，恢复和分叉要完整复制工作区，大工作区会慢。
- 磁盘配额要在宿主目录上另外实现。
