# ADR-005：单一事件源，沙箱与检查点事件写进引擎日志

**状态**：已采纳，待 M0 验证
**日期**：2026-10-21
**决策人**：wangl

---

## 背景

客户端通过 WebSocket 订阅一个会话的事件流。事件有两个来源：引擎产生的消息和工具调用事件，以及 Tether 自己产生的沙箱状态变化、检查点创建、准入拒绝、"工作区已重置"这类说明。其中一部分说明还要让模型看到，例如沙箱从检查点重建后，要告诉模型哪些操作在当前环境里没有发生。

`pi-durable` 允许提交自定义 `kind` 的条目：只有 `kind` 和 `data` 的条目立即追加、模型不可见；带 `model` 字段的条目在下一个边界放入、模型可见。

---

## 备选方案

| 维度 | A：两个事件源，在推送时合并 | B：Tether 事件写成引擎里的条目 |
|---|---|---|
| 事件顺序 | 两路合并，先后关系要另外维护 | 和对话在同一条提交线上，天然一致 |
| 崩溃后 | 内存里的事件可能丢失，或要另建持久化 | 和对话一起持久化 |
| 让模型看到说明 | 要另外实现注入机制 | 就是一条模型可见的条目 |
| 对引擎接口的要求 | 无 | AgentEngine 要提供"追加条目"的能力 |

---

## 决策

选择 **方案 B**。沙箱状态变化、检查点、准入拒绝和各种说明，全部写成 `kind` 以 `tether.` 开头的条目，进入引擎的持久化日志；事件流只有一个来源。

AgentEngine 接口因此要提供追加条目的能力（模型可见与不可见两种），第二阶段的自研引擎必须实现，AgentEngine 一致性测试覆盖这一点。M0 的 Task 7 验证 `pi-durable` 上两种条目的可见性。

---

## 后果

**正面**：
- 客户端看到的事件顺序和会话一致，重连拿到的快照里也包含这些事件。
- "环境与对话不一致时告诉模型"这条原则有了统一的实现方式。
- 不需要第二套事件持久化。

**负面**：
- 引擎接口变宽：自研引擎必须支持自定义条目，以及"立即追加"和"边界处放入"两种时机。
- 会话记录里混入了运行时的事件，读取历史的客户端需要按 `kind` 过滤。
