# ADR-002：harness 不进沙箱

**状态**：已采纳
**日期**：2026-10-20
**决策人**：wangl

---

## 背景

服务端 agent 的工具调用要在隔离的沙箱里执行。harness（组装上下文、调用模型、调度工具、保存会话的那部分程序）可以放在两个位置：和工具一起进沙箱，或者留在服务端，只把工具执行送进沙箱。

这个位置决定了三条边界：模型 API key 等凭据在哪里，会话状态在哪里，资源在什么时候被占用。Tether 的目标场景是多租户的服务端 agent，会话要长期保存、崩溃后能续上，凭据不能被模型写出的命令读到。

---

## 备选方案

| 维度 | A：harness 进沙箱 | B：harness 不进沙箱 |
|---|---|---|
| 凭据 | key 要进沙箱，或者另架出站代理注入 | 天然留在服务端 |
| 会话状态 | 在容器里，容器没了就没了，除非 harness 自己同步出去 | 在服务端存储里，沙箱可随时重建 |
| 资源占用 | 等模型响应时容器也一直开着 | 只在工具执行时需要沙箱，闲置时可以停止 |
| 工具调用延迟 | 本地调用 | 每次跨一次进程边界 |
| 一致性问题 | 没有：两份状态同生同灭 | 有：会话可回滚、文件系统不能；崩溃后旧命令可能还在跑 |
| 复用现成 CLI agent | 直接放进容器 | 需要改造 |

---

## 决策

选择 **方案 B**：agent 循环、会话状态、凭据都在服务端，沙箱只负责执行工具。

多租户、会话要持久化的服务端场景下，B 的三条边界都和沙箱边界重合，不需要额外机制。B 带来的两项代价是 Tether 第一阶段主要要解决的问题：跨进程调用由执行通道承担（ADR-007 的连接与隔离），状态对齐由检查点（ADR-006）和 epoch 隔离（ADR-007）承担。

harness 进沙箱不作为第一阶段的执行模式，以后可以作为对照实现。

---

## 后果

**正面**：
- 模型服务的 key、会话存储、其他会话的数据都不在沙箱的可见范围内。
- 沙箱可以随时销毁重建，会话不受影响；服务端崩溃后从存储续跑。
- 闲置会话的沙箱可以停止，服务端用很少的资源同时运行大量会话的 agent 循环。

**负面**：
- 每次文件读写和命令执行都是一次远程调用。本地 Docker 后端影响很小，以后接远程后端时要实测往返延迟。
- 会话和沙箱两份状态需要检查点、epoch 隔离、重建说明这些机制来对齐，并且要用混沌测试验证。
- 现成的命令行 agent 不能直接拿来用。
