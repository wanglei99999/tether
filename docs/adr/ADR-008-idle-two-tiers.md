# ADR-008：闲置分两档，停止容器时写说明

**状态**：已采纳
**日期**：2026-10-21
**决策人**：wangl

---

## 背景

会话闲置时，它的沙箱仍然占着资源。Docker 后端有两种回收手段：`docker pause` 冻结进程，内存仍然占着，对单机节省不了资源；`docker stop` 结束所有进程、释放内存，文件系统保留。

编码 agent 经常用 `npm run dev &`、`nohup` 启动后台服务，之后再去测它。会话闲置不等于沙箱里没有进程在跑。

曾经考虑过"闲置就直接 `docker stop`"，理由是"闲置期间本来就没有在跑的命令"。这个理由不成立，直接停止会让模型回来时面对一个后台服务已经消失、自己却不知道的环境。

---

## 备选方案

| 维度 | A：闲置即 pause | B：闲置即 stop | C：两档：先保持，再 stop 并写说明，最后删除 |
|---|---|---|---|
| 释放内存 | 否 | 是 | 超过阈值后是 |
| 短暂离开后后台服务还在 | 是 | 否 | 是 |
| 模型是否知道环境变了 | 无变化 | 不知道 | 知道 |
| 宿主重启后 | pause 失效 | 无影响 | 无影响 |

---

## 决策

选择 **方案 C**：

- 闲置不到 `stopAfter`（默认 1 小时）：不做任何事，容器继续运行。
- 闲置超过 `stopAfter`：`docker stop`，同时写一条模型可见的 `tether.sandbox` 条目："容器因闲置被停止，此前启动的后台进程已结束"。下次工具调用时启动容器。
- 闲置超过 `destroyAfter`（默认 7 天）：检查点策略不是 `none` 时先打一次最终快照，然后删除容器；之后再来消息，从快照重建。
- 以后接 E2B / CubeSandbox 时，"停止"映射为它们的暂停（含内存），能保住进程，说明条目相应调整。

两个时长都可配置。

---

## 后果

**正面**：
- 用户短时间离开再回来，环境和离开时一样。
- 长时间闲置的会话真正释放内存。
- 环境变化一定会告诉模型，符合"永远不假装环境还是原来的样子"的原则。

**负面**：
- 闲置不到 1 小时的会话一直占着内存，同时活跃的会话多时需要准入控制（`maxRunningSandboxes`）兜底。
- 停止后再启动，需要重新建立连接，会经过一次 epoch 隔离（ADR-007）。
